# Owned-route configuration API (#641 / THE-17)

This opt-in management API saves complete immutable configuration revisions and publishes a pointer for future composition. Publication never changes `catalog_models`, `catalog_routes`, IAM snapshots, discovery metadata or the default gateway. The unmerged opt-in core PR #1007 is a semantic prerequisite for later execution, not a claimed merged dependency.

## Authorization and privacy

An active SSO human is authenticated before request body access. Current policy attachments are resolved for every request. `routing:ReadConfiguration`, `routing:WriteConfiguration`, `routing:ImportConfiguration` and `routing:PublishConfiguration` act on `routing-configuration:organization`; no administrator bypass exists. Import requires both write and import permission. Explicit Deny overrides Allow; missing permission denies. Revocation affects the next request; a request uses its captured policy versions.

Trusted deployment configuration, never an HTTP body, supplies exact administrator-approved provider registrations (ID, kind, HTTPS origin, secret-manager credential reference) and model mappings (alias, transport provider, final provider, upstream model and verified OpenRouter slug). A saved revision is revalidated against current attestations at publish and rollback. No health, quota, reservation or live mapping guarantee is inferred from configuration.

Provider IDs, route IDs and aliases are unique in a revision; candidate IDs and destinations are unique within each route. Lower safe integer priority wins; stable candidate ID ties follow the core contract. Unknown fields and duplicate destinations reject. Credential references must match the trusted registry exactly; raw key fields are rejected. Jev settings are `{ enabled: false, environment: 'research', sharePrompt: boolean }`, defaulting to false/private. Consent metadata grants no external-call authority. No prompt/response content, tokens, credential references, raw bodies or caller-provided error strings enter administrative audit or errors.

## Revision and publication

All four operations use `POST /management/v1/routing-configurations/{create|read|import|publish}` with Bearer SSO authentication, JSON input (identity content encoding only), no query parameters and no-store responses. Bodies have a 256 KiB/15 second bound with strict UTF-8, cancellation and unknown-field rejection. `create` accepts `{ configuration }`; `read` accepts `{ revision }` (null reads publication metadata only); `import` accepts `{ configuration, source: { routeId, version } }`; `publish` accepts `{ revision, expectedRevision, expectedGeneration }`. Create/import return 201 with a numeric revision; read returns publication plus the requested configuration/provenance; publish returns revision/generation. Fixed errors use 400 invalid_request, 401 unauthorized, 403 forbidden, 404 not_found, 409 publication_conflict or 503 configuration_unavailable. Neither tokens nor caller body fields appear in error messages.

Configuration is `{ schemaVersion: 1, providers, routes }`. Providers carry `{ id, kind, origin, credentialRef }`, with kind openai/anthropic/google/openrouter. Routes carry `{ id, alias, strategy: 'administrator-priority', candidates, research? }`; candidates carry `{ id, transportProviderId, providerId, upstreamModelId, providerSlug, priority }`. Direct candidates require the same transport/final provider and null slug; OpenRouter requires an approved nonnull final-provider slug. At most 128 providers, routes and candidates per route are admitted. Registry approval data is loaded afresh inside each write/publication transaction and is never accepted from the caller. Deployment must make registry replacement coherent with its transaction-aware loader; this API does not provision attestations or claim a live discovery source.

Draft creation stores schema version 1, complete providers and owned routes, plus optional verified legacy provenance. Each route declares alias, ID, candidates, deterministic administrator-priority strategy and bounded disabled research settings. Configuration revisions cannot be edited or deleted by this API.

Publication and rollback require target revision, expected current published revision (null initially) and expected publication generation (zero initially). One transaction locks the singleton publication row, validates the target against current registry attestations, compares both expected values, updates the pointer/generation and appends an allowlisted audit event. A stale request returns conflict without overwriting; failed audit/SQL rolls back both mutation and audit. Republishing an old revision is rollback and increments generation, preventing ABA. Failed COMMIT acknowledgements may represent a committed mutation: re-read state rather than blind retry.

Reads require explicit read permission and mandatory audit, return one requested revision or current publication state, and never expose unattested/unvalidated persisted JSON. Successful create/import/read/publish and permission denials are durably attributed to request/principal/policy versions. Authentication failures contain only request and bounded operation metadata. Database/audit failures return fixed sanitized unavailable errors and no successful result.

## Migration and operational boundary

Legacy import is an explicitly authorized draft operation. It reads an exact existing managed/delegated route and version from storage, preserves that source snapshot plus current policy versions as provenance, and accepts an explicitly supplied replacement owned configuration only if its alias and approved destinations correspond exactly to the legacy source. Unsupported strategy semantics, missing mappings and ambiguous conversion reject rather than infer. No legacy Jev credential, setting or prompt content is copied. Publication remains a separate operation; no legacy/discovery/policy record is modified.

The additive migration can be applied with the existing checksummed migration runner; it creates empty revision/audit tables and an unpublished generation-zero pointer. Operational rollback disables this API and retains historical tables and the complete migration 001–015 bundle/manifest. A pre-015 binary with a shorter migration manifest will fail the existing history-mismatch guard against an upgraded database; retain the upgraded migration runner when disabling the endpoint. Dropping tables, deleting history or blindly deploying an older bundle is unsupported. API fixture acceptance does not establish UI, installed PostgreSQL, operational readiness or complete OpenRouter compatibility.
