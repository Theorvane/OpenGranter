# Issued-token revocation handoff (#640)

The existing combined token management mount exposes **Review issued token revocation** only after successful issuance. It transfers only the validated nonsecret credential ID to the sibling revocation review. It never transfers the bearer token, stores credentials, fetches inventory or changes IAM. The user is warned that activating the handoff clears the displayed token. Live and retained secret nodes are cleared synchronously before the handoff callback. Clearing or canceling does not revoke the token.

The revocation panel exposes `review(credentialId): boolean`. Invalid IDs, pending mutation, terminal denial and disposed mounts return false without replacing the current workflow. Accepted review invalidates old confirmations, clears retained manual input and focuses the existing separate **Confirm revocation** button. Only that confirmation sends the existing no-store revoke POST. Native text rendering preserves opaque identifiers without HTML interpretation. A new review may replace an unsubmitted review, not an in-flight mutation.

Issuance's optional third argument receives exactly one credential ID and returns acceptance. Standalone two-argument mounts remain compatible. Rejected/throwing hosts produce a generic message, never diagnostic text, and cannot redisplay the cleared secret. Reentrant host disposal stays terminal. Combined mounting uses the same guarded request; fresh 401/403 clears both panels. Transport/audit uncertainty never becomes reported success or automatic replay. Cleanup is not rollback and never establishes mutation outcomes.

Local signed synthetic SSO, owned HTTP and embedded PostgreSQL exercise allowed, fresh explicit Deny, deactivated identity and unavailable durable audit. These tests are not company IdP login, installed PostgreSQL, external URL, provider calls or deployment certification. Session approval and exact-head formal review/required CI remain independent gates.
