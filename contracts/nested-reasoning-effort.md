# Delegated nested reasoning effort

Both chat bases accept optional reasoning.effort with max, xhigh, high, medium,
low, minimal, none or null for delegated OpenRouter nonstream and existing
ordinary text streams. The same immutable object may include optional summary.
Preserve absent keys, empty objects, null and exact named values without default
injection, alias rewriting or response fabrication. Own undefined values,
malformed strings/types and other control keys reject before routing.

Top-level reasoning_effort retains its existing null/omission normalization.
When both forwarded effort fields are present, identical named strings are
permitted and preserved in their original positions; differing strings reject
before routing/credentials rather than choose precedence. Nested null with a
forwarded shorthand string is outside this local bounded subset until null
interaction is clarified. It is not asserted to be an official null conflict
rule. Omitted/normalized-away shorthand plus nested null remains supported.

Capture request aliases and nested fields once before async work, compare their
already-validated snapshots, and freeze projected configurations. Mutation during
secret resolution cannot change agreement or the final payload. Client preferences
remain untrusted data without model/provider/region, policy or tool authority.
Complete function/result and opaque reasoning histories retain their validation;
tool streams remain unsupported. All direct OpenAI/Anthropic/Gemini structured
configurations reject before credentials; existing native shorthand support stays
separate and unchanged.

Shared authentication, complete destination IAM/Deny, limits, required audit/usage
and safe possible-billing outcomes remain effective. Stream final usage/DONE remain
persistence gated. No effort, history, prompt, response or credential enters
operational records/errors. No cost, usage or generated reasoning is inferred.

Official ChatRequest.reasoning has optional nullable effort and summary with no
default. The top-level shorthand description forbids simultaneous differing effort
values, without assigning precedence or explaining null interaction. The SDK
serializes differing aliases without enforcing the restriction, so the gateway
checks it. SDK open enums are broader than this bounded named subset. Sources:
[official OpenAPI](https://openrouter.ai/openapi.json) and
[reasoning guide](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

Pin v18 already selects whole inline effort/summary structure and remains unchanged.
The differing-value rule is prose stripped as an annotation; structural drift alone
does not detect prose-only alias changes. Actual SDK sockets cover supported nested
states/equal aliases and reject different aliases on both bases/modes. Model support
and defaults vary. Null interactions, budgets/enabled/legacy controls,
native mappings and complete instance/external-client certification stay open #116.
