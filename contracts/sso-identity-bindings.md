# Pre-registered SSO identity binding read foundation

Issue #486. Plan: [486-sso-identity-bindings](../docs/plans/486-sso-identity-bindings.md).

The contributor selected administrator-pre-registered OIDC issuer/subject bindings and API-specific SSO JWT access tokens for the first human-only management API. Migration `011` stores exact issuer/subject keys mapped to existing IAM principals. Keys use `C` collation, a composite primary key and a restricting principal foreign key. Multiple bindings may name one principal; no binding or human account is created during resolution.

`createPostgresSsoIdentityBindingReader` exposes `resolveHumanPrincipal({ issuer, subject })` to trusted application code after a future access-token verifier establishes identity. This is not JWT verification or authentication. A single parameterized joined query reads current binding/principal kind/active state. Only an active human returns its principal ID; missing mappings, inactive humans and services return `undefined`. No email/username fallback, trimming, case folding, URL normalization or cross-issuer subject matching occurs.

Own required issuer/subject values are captured once before SQL. Local opaque-string bounds are 1–2048 UTF-16 units for issuer and 1–256 for subject, excluding NUL and ill-formed Unicode; exact blanks/Unicode remain identity data. Storage uses character-count checks as a coarse bound; the reader enforces the stricter UTF-16 bound. These are local read bounds, not the selected JWT/access-token claim or issuer-trust profile. Extra caller principal/kind/active/token fields are ignored; projected parameters are frozen and only the validated principal ID is returned.

Invalid inputs throw `InvalidSsoIdentityBindingInput` with message `Invalid SSO identity binding input` before SQL. Duplicate/malformed/inconsistent results, mismatched returned binding keys, malformed principal data or query/result getter failures throw `SsoIdentityBindingUnavailable` with message `SSO identity binding unavailable`. Required result fields must be own properties and are captured once; principal IDs must satisfy the same 1–256 UTF-16, non-NUL, well-formed bound. Errors expose neither raw issuer/subject/driver messages nor causes. Read results are not cached; next calls see changes. Concurrent changes after the statement are not revalidated.

The reader makes no HTTP/key/secret/inference/mutation/audit/usage calls and grants no policy rights. Existing IAM and required decision audit remain necessary at management boundaries. Signature, issuer/audience/algorithm/JWKS/rotation/token-type/expiry/skew checks, access-token versus ID-token rejection, public HTTP authentication/errors/audit and audited binding provisioning remain separate implementation. Current proxy authentication, human/service token lifetimes, discovery/routing and all three OpenRouter pins stay unchanged.

Sources: [OIDC issuer+subject stability](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability), [JWT access-token profile](https://www.rfc-editor.org/rfc/rfc9068.html). The OIDC ID-token subject bound is not silently applied as an access-token profile.
